# B2B1: protected private candidate transfer

This is a bounded offline candidate on the reviewed B2A/A4 baseline, not a
consumer-ready release. No frozen `schema/v1` bytes change. B2B2 composed safe-read
retry, native qualification and independent final-candidate review remain separate.

## Trusted bindings, not caller selectors

`OwnerOptions.PrivateCandidates` installs a `CandidateBinding` for an exact
registered adapter artifact. Its `CandidateRepository` and `Expiry` callback are
trusted owner configuration. `CandidateScope` binds authority, authenticated
caller, request/operation version and digest, adapter artifact, claim and epoch,
lease/invocation, step, direction, parent lifetime and lease deadline. Public
requests gain no path, profile, URL, credential or expiry selector.

`CandidateInline` remains `{mode,value}` and `CandidateStaged` remains
`{mode,candidateRef,bytes,privateDigest}`. There is no wire expiry. Both private
modes require explicit qualification: `ProtectedProducerExpiry` accepts finite
protected producer metadata for staged input and refuses inline input without
such metadata. An inline provider needs its own qualified callback. Staging
provenance is never account identity proof. Existing in-process adapter outputs
and proof callbacks remain supported.

## Protected staging and bounded decoding

`NewProtectedCandidateFiles` fixes a trusted binding and absolute private
staging directory. The Darwin implementation reuses the existing APFS/HFS
custody helpers: caller-owned 0700 root, safe ancestors, caller-owned 0600 regular
files, one link and inode/path agreement. References are random 32-character
lowercase hexadecimal names. Traversal, symlinks, hardlinks and non-regular files
are refused. Reads use `O_NOFOLLOW|O_NONBLOCK` plus pre/post descriptor checks so
an untrusted special-file name cannot block an ordinary FIFO open. This does not
claim isolation from a hostile process with the same UID, nor an interruptible
kernel I/O deadline on a failed filesystem.

A fixed magic and bounded closed metadata header precede raw candidate bytes.
Reads are capped at the registered operation maximum plus a one-byte overflow
probe; declared bytes and SHA256 must exactly match. Strict JSON decoding rejects
malformed, duplicate-key and unknown schema members. Before typed decoding, the
header and nested scope must have exactly the canonical required key sets.
Wrong-case names, case aliases, missing/unknown fields and escaped duplicate keys
are refused, so Go's case-insensitive struct matching cannot overwrite expiry or
scope. Canonical Write spelling is unchanged. Transport digest/length are
separate from the canonical semantic fingerprint, so alternate JSON escaping or
spacing cannot evade current or historical rejected-candidate fences.

Unsupported operating systems fail closed. Provider files and directories are
not discovered or created by this resolver. Interrupted writes may leave private
unreferenced staging files; no automatic destructive cleanup or new daemon was
added. Retention cleanup requires the owning host's separately qualified policy.

## Durable acceptance and restart

An incoming result is admitted only after the existing before-effect checkpoint.
The exact validated bytes, decoded candidate, semantic fingerprint, finite
qualified expiry, scope and original acceptance transaction ID are durably
reserved through the invocation's existing backend guard before acceptance.
Neither transfer acceptance nor reconciliation acquires that guard recursively.

A positive receipt and matching readback are required before exposing the
candidate to recovery. A fresh exact same-claim resume reconciles the original
transaction ID. Positive committed readback restores its accepted record;
positive noncommitted readback permits acceptance of the retained immutable
material. Unknown outcome blocks. No restart re-reads the producer file,
re-qualifies a later expiry, refunds a provider permit or recaptures credentials.
Claim handoff retains transfer identity, effects, attempt counters, rejection
fences and the exact candidate/proof binding. Typed reconciliation can carry
`RecoveryReconcileResult.CandidateTransferID` for the same validated handoff.

## Opposite-direction proof handoff

`InvokeFrame` first verifies the inline representation against the registered
private frame cap. If a valid candidate does not fit, the same fixed trusted
repository writes a bounded staged representation. The grant is durably reserved
before issuance; failed or uncertain publication does not yield a frame or allow
an in-memory invocation retry. If even the staged descriptor cannot fit, it fails
rather than increasing a cap or changing transport.

The installed local private adapter bridge uses `StagingScope` for producer
metadata and `ConsumeStagedCandidate` for an outbound candidate. That method
validates the exact scope, transport and decoded candidate under the existing
guard, then durably prepares an original delivery transaction ID before attempting
the delivered transition. It returns bytes only after positive exact readback and
a final lifetime check. A refused attempted consume cannot be revived with a new
caller context, and a proof checkpoint for a staged grant requires successful
local delivery. Raw repository
`Read` is a transport helper, not an authorization to consume a grant or perform a
provider effect. A real child bridge must implement this trusted local handoff;
no public RPC accessor or standalone staging service is added here.

Repository reads and all delivery storage work share the minimum of the exact
private lease, candidate expiry, caller deadline and original invocation/channel
lifetime. A new caller context cannot extend these bounds. Parent loss signals
cancellation without acquiring the session mutex, including during pending
repository/storage callbacks. Liveness is checked after reading, before each
transition, immediately before the backend commit and before nonempty return.
Private handoff storage never detaches cancellation for a cleanup allowance.
Existing non-handoff intent and cleanup behavior remains unchanged. A backend
that completes a write after cancellation can leave durable transition evidence,
but cannot make the owner return candidate bytes or issue proof permission.

On exact resume, old outbound grants require original issuance, delivery and
retirement transaction readback, not just the issuance receipt. Delivery and
retirement each have guarded durable preparation with immutable transaction ID,
request-journal/digest and source/destination state. Failed later bookkeeping
cannot erase the original attempted transaction identity. Unknown receipts block
retirement/new issuance even if a committed marker was stored. Positive local
noncommit allows completing retirement under its original ID; it never retries
an old consume or restores an old reference. A known noncommitted delivery is
retained as such while its old grant is retired. All retained transition
identities must survive authoritative readback unchanged.

A retired old lease is never revived. Only a fresh, exact same-claim resume with
resolved local transitions and the existing claim/effect authority may produce
a new grant for the retained candidate. Issued effect permissions, attempt
counts, exact expiry and security fences are not refunded, reset or recaptured.

## Evidence and limits

The B2B1 receipt records exact executed tests and source hashes. Synthetic cases
cover protected-file and private-FD positives, a 6000-byte proof candidate under a
4096-byte frame cap, explicit inline expiry, wrong artifact/lease/caller/claim,
missing resolver, hash/length mismatch, expired input, malformed/schema-invalid
JSON, exact/+1 operation caps, semantic rejection, replay and concurrent accept,
cancellation, parent loss, FIFO/symlink/hardlink/mode refusal, uncertain inbound
and outbound commits, same-owner/fresh-owner resume and protected backend reopen.
Restart tests remove the producer file before continuation to prove retained
material, not a fresh read, owns acceptance. Public results do not contain the
synthetic private candidate.

Non-temporal private-frame tests use the existing owner-local controlled deadline
seam. Production still uses `context.WithDeadline`; no phase/RPC/cleanup limits
were increased. Explicit expiry/cancellation/deadline tests remain part of the
full gate. Earlier failed gates and their specific diagnoses are retained.

The staged child fixture uses an owned in-memory duplex descriptor. Existing
backend/IPC subprocess crash tests remain in the full suite, but no new
staged-transfer process-kill matrix or real provider/SDK/native-store test is
claimed. Exhaustive power-loss points, foreign UID attacks, unsupported-platform
custody, hostile same-UID protection and every native child bridge remain
unqualified. No root gate, publication, integration, consumer update, provider
request, configuration, service or schedule action is included.

## B2B1a review corrections and remaining qualification

The earlier file review's F1 was static, with its Go probe denied before it ran.
Its prepared test and refusal remain unexecuted history. The owner correction
uses new exact-key regression tests on corrected source through the unchanged
approved route; it does not replay that denied command. The separate executed
STATE-1 memory-only red proof remains preserved alongside the corrected-source
lease/read/storage/cancellation regressions.

New controlled tests cover earlier caller/invocation/candidate bounds, lease
expiry inside Read and storage, parent loss while Read or storage is pending,
pre-delivery and post-commit refusal, positive delivery, same-session duplicate
and concurrent consumption, fresh-context retry refusal, and zero proof permits
after refusal. Delivery/retirement tests exercise unknown, committed and proved
noncommitted outcomes, later bookkeeping failures, fresh owners and reopened
protected backends, retaining exact original IDs and no acquisition replay.
These tests are not an exhaustive process-kill or native-child bridge matrix.

Darwin ACLs, including inherited ACLs on ancestors, roots and files, are not
inspected. Mode/UID checks alone do not establish cross-UID confidentiality.
Stable private roots remain a trusted host assumption: paths are checked by name,
not held by stable directory descriptors for every operation. Rename/in-place
mutation/TOCTOU, foreign-UID attacks, hostile same-UID isolation and power-loss
semantics remain unqualified. This does not narrow the exact closed-metadata
contract, which is enforced in source. No real native FD3 child bridge, provider,
SDK, account proof, new process-kill matrix or consumer activation was performed.
