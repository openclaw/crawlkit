# B2C2: metadata-settlement finalization and safe errors

This offline candidate implements the coordinator-selected private delivery
contract for `Owner.SettleReadComposition`. It changes only that function's
finalization/error-return integration and one narrow private normalization helper.
It does not change Guard, backend/commit, dependency graphs, business entrypoints,
recovery, cookie/adapter logic, FD3 fixtures, wire schemas or Node inputs. The late
partial contract-review advice is retained as late and unverified, not accepted
retroactively; the separately recorded coordinator contract owns this decision.

## Release and delivery precedence

A successfully acquired guard is closed exactly once by the owned finalizer.
Final delivery is evaluated after that close and before stopping the current
control context. The existing two-second control and 250ms queue bounds remain
unchanged. The finalizer does not retry release, force an unlock or schedule work;
Guard.Close's closed-bit and failure semantics are unchanged.

The final decision has this order:

1. An existing body error remains primary after safe normalization. Return an
   entirely empty `ReadSettlementStatus`, preserving its recognized safe core code
   rather than replacing it with a later cancellation or release error.
2. Without a body error, the current `compositionContextError` governs every
   status, including `blocked`. Existing deadline-versus-cancellation precedence
   remains. A lifetime error returns an empty status. A nil-error blocked status
   is metadata, not a preexisting error or permission to ignore the current lifetime.
3. Without a body or lifetime error, a release failure returns an empty status and
   `StorageFailure` with fixed private detail `settlement_guard_release`.
4. Otherwise, return the original live status unchanged.

If release also fails under a higher-priority body or lifetime error, retain the
primary code and use the safe finite combined diagnostic described below. The
final-status boundary hook remains after release, with no business callback or
new deadline. A known committed preparation, resolution or original outcome is
not rewritten because its current control delivery failed. No fabricated negative
certainty, permit refund, competing transaction ID or new continuation follows.

A fresh confirming control is a separate explicit same-caller invocation, with
normal authorization, a new current capability and its own unchanged bounds. It
is not a retry performed inside the failed control, an old-parent revival or a
new capability granted by a blocked route diagnostic.

## Private error vocabulary and provenance

The new unexported `settlementControlError` returns a newly allocated safe `Error`.
It never forwards an arbitrary error object, joins raw errors or blindly trusts
`ErrorCode` on a backend-controlled typed error. Only direct non-nil `*Error`
values with explicitly enumerated core codes can retain their code. The vocabulary
is the existing fixed core codes plus `deadline_exceeded` and
`unsupported_operation`; raw/wrapped/non-core/unknown-code errors become
`StorageFailure`. No error category is added.

Direct backend Acquire and Load failures are normalized at those return boundaries.
Even a recognized safe code cannot supply a private detail: the detail becomes
`settlement_storage`. Thus `OwnerBusy` can remain the primary code without exposing
a backend's text or exported `Detail` field. Unknown typed `Code` strings are not
allowed to escape merely because `Error.Error()` normally hides the detail.

Core-origin errors retain only an enumerated fixed diagnostic vocabulary. Necessary
scope anchors such as `settlement_claim_origin`, `settlement_claim_anchor`,
`settlement_scope`, artifact/identity anchors, authorization and current lifetime
diagnostics remain available. Other unlisted private details become
`settlement_control_error`. This is a documented private diagnostic narrowing,
not a public wire or global ErrorCode change.

When release also fails, `_guard_release` is appended only to an already fixed or
allowlisted detail. Examples are `settlement_authorization_guard_release`,
`settlement_storage_guard_release` and the fixed lifetime variants. No raw release
text is joined or wrapped. An origin anchor is unchanged when release succeeds;
its combined form remains a finite safe diagnostic when release also fails.

Existing graph/commit helpers may convert a readback error into a fixed live
`blocked` status. That is still not a body error: lifetime and release precedence
apply to its delivery. This slice does not change those helpers or reinterpret an
uncertain original transaction as noncommitted.
