# B2B2: explicit owner safe-read composition (partial)

This offline candidate implements the live-parent path and fail-closed durable
readback. It does not complete pending continuation after a lost parent, full
conformance, native integration, distribution or runtime qualification.

## Opt-in authority

`OwnerOptions.ReadRecoveryOperations` enrolls exact registered safe-read operation
IDs/versions. `ReadRecoveryAuthorization` supplies a trusted approval reference,
not permission by itself: the existing Authorizer Allow and Recovery checks must
approve the actual internal recovery request. Operation, plan, adapter artifact,
transport and transport descriptor come from the immutable owner registry.
Mutation, inspect/control and recovery requests cannot use this entry point;
publicly supplied operation/plan objects or extra selectors are refused.

`Owner.HandleWithRecovery` is explicitly called by the trusted host. Ordinary
`Handle` remains non-composing, even when an operation is enrolled. A selected
zero-retry plan performs once without recovery. The old `SafeReadRetry` callback
utility remains compatible but is not used as this implementation's authority.
No frozen public/private schema or normative manifest bytes changed.

## One guard, original request and existing recovery

The original Perform journal owns a private `ReadComposition`. Its immutable
operation fingerprints, accepted deadline, selected plan, identity fingerprint,
internal request IDs and final transaction ID are retained in the existing
snapshot. Linked internal journals hold the initial Perform diagnosis, recovery
and single retry. The original request/target/args remain unchanged; the final
response uses its original correlation, receipt and accepted generation, with
the observed final generation after adoption.

One existing backend guard encloses the live sequence. Internal invocations use
`performInvocation`, `recover`, ordinary intent preparation, claim/candidate
proof and adoption, not recursive Handle or a second manager/lock/store. Only an
actual completed safe-read `needs_login` or `rejected_generation` diagnosis can
trigger recovery. Throttle, challenge, permission, scope/account, malformed,
storage/uncertain, cancellation and budget failures cannot become new login.
A second authentication rejection is terminal for this composition.

An existing exact caller/epoch/cause claim may be resumed with real recovery
approval and its retained candidate/proof. Starting an initial read while another
claim is active still requires the existing separately qualified uncertainty-safe
read option; enrollment in composition does not bypass that fence. Adoption must
have exact positive commit readback and preserve the enrolled identity before a
retry is created. Retry allowance is reserved durably with its single child
journal before a provider intent can be issued. Claimed attempts and security,
maintenance, cooldown and candidate/transition fences are not reset.

## Deadlines and conservative shared accounting

The root stores the original accepted deadline, including the tighter initial
caller context. Initial read reserves the recovery/final-read phase window;
recovery receives a shorter child window that retains time for the final read
and cleanup. Per-phase/RPC/native ceilings remain registry-owned and can only be
intersected downward. No wait loop, new deadline, second recovery, alternate
transport or mutation replay is added. Composition storage uses the existing
strict bounded context rather than detaching canceled work for extra cleanup.

Every committed effect intent atomically charges one request and reserves that
operation's registered `maxProviderBodyBytes` in the linked journal. Shared
request and byte ceilings are derived from these retained journals. This is a
conservative worst-case reservation, not an assertion of actual network bytes:
unused response capacity is not refunded. Native body acceptance remains capped,
and private budget frames show the minimum native/shared remaining allowance.
This avoids losing already-consumed byte allowance through failed post-response
bookkeeping but can refuse a workload whose small actual responses would fit;
real operation registries must qualify this policy. No universal cap replaces a
native operation's registered body or cursor maximum.

The original active operation receives child effect certainty, so cancellation
of the original request cannot report withdrawn-before-effect after a child
obtained a provider permit. Caller/channel cancellation and expired phase/outer
bounds prevent further acquisition, proof or retry, even if a callback returns
late. A stored successful adoption is not permission for a late read retry.

## Exact outcomes and the remaining continuation gap

Composed child-result and root-final transaction IDs are durably prepared before
their writes. Root final outcomes require exact receipt/readback, including on
fresh-owner dedup. Unknown issuance/adoption/result outcomes remain fenced with
their original identities despite later bookkeeping failures. A committed read
permit without a retained result is never blindly replayed.

**Pending interruption is readback-only.** The current frozen Perform request and
Authorizer provide caller identity but no durable attestation that the original
invocation/parent is still live. A new context is not that attestation. Therefore
same-request/fresh-owner calls may reconcile original IDs and return a completed
final result, but they never continue pending reads/recovery/retry. Even proved
noncommit does not invent new parent authority. Expired original Perform work
cannot be revived by a larger deadline on the same request.

This is an explicit B2B2 partial, not completed restart orchestration. Pending
records can continue fencing ordinary work and require separately authorized
resolution. A later admission must either qualify a trusted durable parent/
continuation contract or specify a separately authorized terminal abandonment/
reconciliation route that cannot revive the expired Perform or refund effects.
No new wire field or implicit lifetime policy is invented here.

## Executed evidence and limits

The exact receipt separates initial success, one recovery/retry, second rejection,
noneligible failures, authorization, zero plans, native/shared caps, cooldown,
retained-claim proof, cancellation, correlation and concurrent/deduplicated calls.
Memory and protected-backend reopen faults cover initial intent, adoption, retry
intent and final publication, each stored/nonstored with unknown readback and
later failures. Counts and stage-hit assertions establish no extra effects or
reset allowance; historical final success can be read back without replay.

The source-matched core/race/IPC receipts retain previous red and denied evidence.
No new staged process-kill/power-loss, real FD3 bridge, SDK/provider/account proof,
ACL/foreign-UID/stable-root/TOCTOU qualification or consumer activation is claimed.
Broader malicious-backend corruption and every callback/phase permutation remain
outside this bounded slice. These are the original B2B2 evidence limits, not a
reopening of later B2B2a/B2B2b corrections or named B3a independent closures.
Independent review of subsequent source deltas remains required.

## B2B2a: native total, accounting and final outcome correction

The selected/intersected child `MaxTotalMs` is now an absolute deadline starting
before internal approval-reference lookup, Allow/Recovery authorization and
journal preparation. It intersects the original root/tighter caller/channel
window and reserved retry tail. The clipped deadline is copied into the actual
request, invocation, storage context, provider request context and private lease.
Required remaining phases are revalidated after clipping, authorization and
preparation. The child context continues through adoption and its exact readback;
no later phase starts a new total timer. Default non-composed Handle is unchanged.

The local accounting qualification now performs two actual synthetic requests
and bodies in each initial/acquisition/proof/retry stage. Every external effect
calls BeforeEffect, then uses RequestContext/body handling. RequestContext creates
only a timeout, never another permission or request charge. Exact/+1 request,
shared reserved-byte and native-body limits, private-frame remainder, and
uncertain multi-request protected reopen/no-refund cases are exercised. This
qualifies that explicit trusted-adapter mapping, not an adapter that omits hooks.

Historical final readback now binds the original root/child IDs, operation and
caller links, prepared/stored payloads, receipt digest/generation/revision and
positive terminal-read/adoption witnesses. With the existing guard held, a loaded
snapshot cannot silently substitute another observation. Prepared-to-committed
readback must match the complete proposed snapshot; at an exact committed
revision its native receipt digest is reconstructed. Later legitimate revisions
retain historical receipts and payloads. Targeted contradictions are refused
without effects or fence changes, not treated as fabricated completed results.
This is bounded evidence, not a claim to withstand every arbitrary malicious
backend rewriting all original authority.

### Final delivery precedence

Delivery is permitted at the last liveness check. Cancellation/expiry observed
before that check wins the current delivery, but never rewrites committed history:

- Before a timely, fully validated final readback, refusal is canceled/deadline
  with uncertain certainty; it does not assert no prior effects.
- After the final outcome is positively known but before cache/return, refusal
  retains the known outcome certainty (completed for successful work), original
  receipt and correlation. The successful stored outcome remains unchanged.
- Cached and historical composed outcomes use the same last delivery check,
  including a composed cache accessed through ordinary Handle. A fresh valid
  historical lookup may return the stored outcome without new business effects.
- Cancellation occurring after the final delivery check is ordered after that
  delivery, not claimed to atomically retract already returned bytes.

Controlled callbacks test final storage/readback, pre-cache, post-cache/return and
fresh historical lookup, with cancel and deadline variants. The owner-local test
boundary hook is nil in production and does not change timers, limits or policy.
No terminal settlement, parent-liveness mechanism, new authorization policy or
fence-clearing path is added. Pending lost-parent work remains readback-only and
fenced; non-resuming terminal settlement is the separately selected later scope.

## B2B2b: revision lower bound and pre-entry known-cache refusal

A loaded observation must be at least as recent as every required committed
outcome receipt. An earlier snapshot is refused before equal-revision digest or
historical handling, even when two same-guard observations agree with each other.
The lower bound applies to the root, required child result/adoption witnesses
and global completed-outcome admission. Equal-revision full-state digest checks
remain mandatory; legitimate strictly later metadata and protected reopen retain
historical-result support. A consistent pair of stale observations is not proof
of a committed later outcome.

For pre-entry late delivery, current channel, schema/binding, enrollment and real
Allow/confirmation/recovery checks run first. Only an exact caller/channel/request/
digest match to a terminal, proved composed cache can then supply its original
receipt, certainty and correlation for a failed late-delivery response. Both
HandleWithRecovery and ordinary Handle use this memory-only refusal. It starts
no provider/backend operation, allocates no replacement receipt, creates no new
deadline and cannot return late success. An observed expiry reason is retained;
when the request deadline is already expired, it takes precedence over a canceled
caller context.

Known uncertain and genuinely not-dispatched cached outcomes retain those exact
certainties, never become completed. Pending, unmatched, unauthorized, unenrolled
or invalid cache cases cannot reflect another receipt or clear fences; their
existing unknown/no-cache handling remains unchanged. Positive on-time delivery
is unchanged. The lock order remains channel, owner, active entry, with response
validation/refusal after releasing locks.

The native regressions separately cover the exact seven-case independent proof,
root and child earlier/equal/later receipt bounds, genuine later metadata/protected
reopen, both entry points with cancellation, request/caller expiry and combined
lateness, plus authorization/channel/binding/digest/target and pending-cache
negatives. The original failing harness/log and the independent passing deadline/
accounting probe remain byte-identical. No deadline/accounting rule, terminal
settlement, liveness policy or consumer qualification is added by this correction.

## Subsequent separately admitted B3 candidate

[B3.md](B3.md) now describes the additive offline default-deny, non-resuming
terminal-settlement candidate. Earlier statements selecting settlement for a
later admission record the B2B2 correction boundary, not an automatic policy.
Pending work remains fenced unless that explicit control independently proves
and positively commits its narrow metadata resolution. No old business work is
resumed; unsupported legacy provenance and unknown outcomes still fail closed.

The B3a candidate strengthens only non-resuming terminal metadata dependency and
control boundaries. It does not relax the old business deadline or turn a fresh
caller context into continuation authority. Original interrupted requests remain
non-resumable, with independent fences and separately authorized follow-up intact.
The named independent P1, terminal-receipt, foreign-origin and later-callback
closures, plus the finite residual local contracts, are recorded in B3.md rather
than being inferred from total test counts.

two narrow fixes without changing this composition, deadline, accounting, outcome
or settlement implementation. Its two production fixes now have bounded independent

not reopen closed recovery branches, manufacture a native Node backend, resume an
old parent, or authorize consumer integration.
